# Pizza Ordering System

SOE103 五人小组 C11 项目。仓库地址：<https://github.com/XiaoruChang/pizza_order>。

## 从这里开始

1. 所有人直接使用 `include/` 中同一版本的公共头文件，不自行重复定义公共结构或更改函数签名。
2. 阅读 [公共接口清单](docs/public-api.md)，确认分工、金额、权限、错误码、保存和内存所有权约定。
3. 使用 [组员开发提示词](docs/teamwork.md)，填写个人分支、本地目录、任务和验收标准后交给自己的编程助手执行。
4. 在 `dev/<姓名或用户名>` 开发并提交到 `main` 的 PR，默认由组长审查和合并。

## 当前 main 的范围

当前发布的是公共接口基线：12 个公共头文件、接口规则、协作说明和独立编译检查。
`src/result.c` 已实现错误码说明函数；其余业务函数（包括 `app.h`、`sales.h` 的声明）
尚无实现合入本分支，不能把头文件编译通过视为完整业务完成。

`AppState` 暂为不透明类型。负责公共存储与整合的成员需先与账户、订单、余额成员
统一私有状态结构和事务辅助接口，其他成员不能各自定义不同的 `struct AppState`。
相关业务实现通过后续成员 PR 合入。

## 分工与文件

## 检查公共接口

需要 CMake 3.20+ 和 C11 编译器。Windows MinGW 示例，在仓库根目录执行：

```powershell
cmake -S contracts -B build/contracts -G "MinGW Makefiles"
cmake --build build/contracts
```

Linux/macOS 或 MSVC 可省略生成器参数，并使用相应工具链。
此检查会逐个重复包含 12 个头文件，并以两种顺序组合包含全部头文件，
同时构建错误码说明静态库。开启严格编译警告并视为错误。
它验证公共声明可编译，尚不包含业务运行测试。

后续若根目录已有完整系统的 `CMakeLists.txt`，还需按该实现的说明构建系统并运行测试；
添加自己的源文件时同步维护对应构建目标。

## 主要业务约定

- 金额使用整数分，成功的业务修改在返回前保存。
- 客户只能操作本人账户与订单；经理修改操作要求经理会话。
- 订单与扣款由订单模块统一提交；充值与结算不能各自保存一半状态。
- 历史订单保存成交时的名称和价格；统计使用历史实收小计。
- 公共函数声明、类型或业务含义需要变更时，先说明对其他成员的影响并协调。
- 不提交密码、密钥、本地配置、运行数据和构建产物。
