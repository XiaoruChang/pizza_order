# 组员开发入口与提示词

所有人从同一仓库的最新 `main` 开始，直接使用 `include/` 的公共头文件。
先阅读 [接口文档](public-api.md)，再把下面模板中的本地目录、个人分支、任务及验收标准填完整。
仓库地址已填写；本地目录应是每个组员自己的路径。

当前 main 仅包含接口基线和 `result_message` 实现。账户、菜单、订单、存储等实现通过各成员 PR 补齐；
共享的 `AppState` 内部结构和事务辅助接口需由负责存储与整合的成员先与相关成员统一。
开发任务应注明模块范围与依赖，不能把“能编译公共头文件”作为业务完成的验收标准。

## 可复制的提示词

```text
请在我的电脑上完成本次小组项目开发，从克隆仓库、创建或切换个人分支，一直做到向主仓库提交 Pull Request。

仓库地址：https://github.com/XiaoruChang/pizza_order.git
本地项目目录：<填写我电脑上的本地路径>
我的个人分支：dev/<填写姓名拼音或 GitHub 用户名>
本次开发任务：<填写模块、功能要求、依赖及验收标准>
关联 Issue：<填写编号，没有则写“无”>
PR 目标分支：main

请按以下流程执行：

1. 检查本地目录。如果尚未克隆项目，将仓库克隆到指定目录；如果已经存在，确认 origin 地址与指定仓库一致，避免重复克隆。阅读适用的 AGENTS.md、README.md、docs/public-api.md 和 docs/teamwork.md，了解代码结构、公共接口及本次模块的实现责任。若存在未提交的修改，先辨明归属并保留，不要覆盖或擅自提交。

2. 获取远程最新代码。如果个人分支尚不存在，从 origin/main 创建；如果远程已有个人分支，则建立跟踪关系并切换；如果本地已有，则直接使用，并先同步远程同名分支。随后将 origin/main 合并到个人分支。所有开发和提交都在我的个人分支进行。存在未提交改动时先采用保留原改动的隔离方式处理，不要强行切换或丢弃。

3. 根据本次任务完成实现。直接包含仓库 include/ 中的公共头文件，函数签名、数据结构、错误码、金额单位、权限、内存所有权和保存规则遵循 docs/public-api.md，不重新声明另一套公共类型。发现必须变更其他成员负责的公共接口或共享内部状态约定时，先说明影响并等待协调。若共享 AppState 或跨模块依赖尚未实现，先确认负责成员和既定内部接口，不自行造出互不兼容的状态，也不伪造成功实现。任务不明确时先查代码、Issue 和文档，只有缺少关键信息且无法合理判断时才提问。

4. 执行公共接口检查：cmake -S contracts -B build/contracts，再执行 cmake --build build/contracts；Windows MinGW 可在配置时加 -G "MinGW Makefiles"。若已有完整系统的构建和测试入口，也执行本次改动所需的检查，修复引入的问题，并补充必要的测试和使用说明。添加 .c 文件时维护所属构建目标。提交前检查差异，只暂存本次任务相关文件，排除密钥、本地配置、运行数据和构建产物。使用清晰提交信息，例如 feat(order): implement order submission。

5. 提交 PR 前再次获取远程更新，将最新 origin/main 合并到个人分支，解决冲突并重新执行受影响的检查。不要强制推送、硬重置或丢弃他人修改。将个人分支推送到 origin，首次推送设置上游分支。

6. 使用可用的 GitHub 工具或 gh 创建“我的个人分支 → main”的 PR。同来源和目标分支已有开放 PR 时更新该 PR。PR 使用中文说明本次解决的问题、主要改动、实际检查结果，以及公共接口或数据结构变化。有关联 Issue 时加入 Closes #编号。普通业务修改应明确公共头文件是否保持兼容。

7. 提交 PR 后停止，由组长审查和合并。不要自行合并 PR，也不要删除个人分支。阻止本次任务验收的问题尚未解决时，创建 Draft PR 并说明原因；不要把头文件检查通过当成业务实现成功。缺少登录或权限时保留工作，说明需要完成的具体操作，不把未创建的 PR 说成已提交。

请直接完成上述已授权操作，无需逐步请求确认。最后用中文提供：个人分支名称、提交记录、PR 链接、实际执行的检查，以及任何尚未解决的问题。
```
